# 基于 AI 智能分析的工程运维（安全）决策系统开发与实现方法论  
——以本仓库“工程安全智能决策助手（Construction Safety Assistant）”为落地原型

> 说明：本文依据项目书 `广州大学大学生创新训练项目申报书.docx` 的技术路线与目标，并结合本仓库实现（`app.py`、`rag/`、`llm/`、`analysis/`、`scripts/`、`tests/` 等）撰写。写作目标是给出一条可复查、可复现、可扩展的系统开发主线：从需求—数据—模型—推理—决策—评估—部署的全链路方法论，并对关键技术与关键参数给出“为什么这样选”的解释。

---

## 0. 研究对象与方法论边界

### 0.1 项目书目标到系统落地的“可实现切片”
项目书提出的总体愿景是构建覆盖“风险识别—资源调度—运维决策”的智能化工程运维体系（强调低成本、开源、跨学科融合），并提出多模态融合、边缘计算、知识共享、在线学习等路线。  
本仓库对应的是其中**最先可落地且对工程安全管理价值最高的一段链路**：  

1) **风险识别与事前预判**：基于历史事故知识库 + 环境/传感参数，对即将开展的作业给出风险等级、潜在危险源、预防措施与 PPE；  
2) **知识共享与可追溯决策**：以 RAG（检索增强生成）把“依据（历史案例）”显式附在结论里，形成可追溯的管理建议；  
3) **评估与验证**：提供单元测试、验收脚本，并以轻量 PSM（倾向得分匹配）示范“管理干预的因果效应估计”，为后续工程管理研究提供方法工具链。

> 学术严谨性要求：系统论文/报告必须明确“当前实现范围（MVP）”与“项目书规划能力”的差异；未来扩展（图像/视频、GNN、DRL、数字孪生、联邦学习等）应作为迭代路线描述，而不能在结果章节中当作已实现能力。

### 0.2 设计原则（对应项目书痛点）
项目书痛点可抽象为三类工程约束：  
- **数据割裂与脏乱差**：多源异构、缺失与格式不统一导致难以建模与共享；  
- **外部风险响应慢**：环境/天气/供应链等外部扰动对安全与工期影响显著，但传统系统难以实时吸收；  
- **动态管控不精准**：缺少可解释、可追溯、可闭环的风险研判与处置建议生成机制。  

因此系统原则是：  
1) **统一数据接口 + 明确字段契约（schema）**，优先把“可用数据”变成“可检索、可计算的数据”；  
2) **RAG 优先于纯生成**：结论必须能指向证据（案例 ID），以提升可信度与审计可用性；  
3) **结构化输出优先于自然语言长文**：便于落地到派单、看板、统计分析；  
4) **可用性优先**：无 API Key / 无模型文件时仍可运行（离线规则兜底），符合“低成本、普惠部署”目标；  
5) **可复现性优先**：固定随机种子、提供脚本与测试，避免“演示可用、复跑不可用”。

## 1. 需求工程：从工程运维问题到可计算任务

### 1.1 任务分解（把“管理问题”翻译成“机器任务”）
以“施工作业开始前的风险评估”为核心场景，系统把输入与输出约束化：

**输入（Input Contract）**  
- 作业计划文本（`work_plan`）：描述要做什么、在哪里做、用什么设备/工艺；  
- 工种类型（`trade_type`）：高处、电气、焊接热作、土方开挖、运输机械、起重吊装、拆除、综合施工；  
- 工种专项信息（若干字段）：例如高处作业平台类型、临边防护状态、安全带挂点类型等（见 `app.py` 的 `TRADE_FORM_CONFIG`）；  
- 环境参数（`temp_c`、`wind_speed`、`humidity`）：来自传感器或手动输入（`sensors/api.py`）。

**输出（Output Contract / Schema）**  
系统把“风险评估报告”定义为可机器校验的 JSON：  
- `risk_level`：风险等级 1–4（1=低，4=极高）  
- `potential_hazards`：主要潜在危险源（短语列表）  
- `preventive_measures`：针对性预防措施（可执行列表）  
- `required_ppe`：必需 PPE（列表）  
- `citations`：引用的历史案例 `case_id` 列表（必须来自检索结果）  
- `rationale`：评估理由（解释风险等级为何如此）

> 为什么这是关键：  
> - 需求工程的核心不是“做一个 AI”，而是**定义一个可交付、可验收的输出契约**。  
> - 没有 schema，系统就很难测试、难以上线、难以派单与统计；尤其在工程管理场景，审计与责任追溯要求更高。

### 1.2 风险等级 1–4 的选择理由
项目书与系统都采用 1–4 的离散等级，原因是：
- **管理可操作性**：过细（如 1–10）会导致标注主观性增大、执行策略难以区分；过粗（如 高/低）又难以形成分级响应；  
- **与数据集标签兼容**：本仓库事故数据中存在 `degree_of_inj_x`（1–4）字段，可直接用于统计分析与校准；  
- **便于与应急预案对接**：分级越少，越容易形成 SOP（标准作业程序）与派单映射（见 `dispatch/logic.py`）。

## 2. 总体架构：数据—知识—推理—决策的闭环

### 2.1 四层架构（实现与文件映射）
1) **数据层（Data Layer）**  
   - 历史事故库：`Injury Severity.CSV`（约 53k+ 记录）  
   - 环境/传感数据接口：`sensors/api.py`（当前为 mock，预留 MQTT/HTTP/串口）

2) **知识层（Knowledge Layer / RAG 索引）**  
   - 向量化与索引构建：`rag/index_builder.py`、`rag/embedding.py`  
   - 索引与元数据存储：`indexes/faiss.index`、`indexes/metadata.parquet|jsonl`（`rag/storage.py`）

3) **推理层（Reasoning Layer）**  
   - 检索：`rag/retrieval.py`（语义 + 关键词混合重排）  
   - 提示词模板：`rag/prompting.py`（强制 JSON、强制引用案例、中文输出）  
   - 大模型客户端：`llm/client.py`（DeepSeek OpenAI-compatible 接口）  
   - 结构化抽取校验：`rag/extraction_schema.py`

4) **应用层（Application Layer）**  
   - Web 应用与交互：`app.py`（Streamlit 看板 + 事前预判）  
   - 离线兜底：`rag/local_pre_assessment.py`（规则化风险评估）  
   - 工程化脚本：`scripts/start_app.py`、`launcher.py`（运行与打包）

### 2.2 两条闭环
- **闭环 A：事前预判闭环**  
  采集作业计划与环境 → RAG 检索相似事故 → LLM/规则生成风险报告 → 输出可执行措施与 PPE → 人类执行与复盘（后续可接入反馈采集）

- **闭环 B：评估与迭代闭环**  
  单元测试 + 验收脚本确保可复现 → 统计分析与因果评估（PSM）支持“管理干预是否有效”的研究 → 反哺阈值、检索策略与提示词

## 3. 数据层方法：把“脏乱差”变成“可检索、可建模”

### 3.1 数据字段与最小可用集（Minimum Viable Schema）
系统围绕两类字段：
- **检索必需**：事故文本 `abstract`（配置项 `TEXT_COL="abstract"`，见 `rag/config.py`）  
- **解释与展示**：`event_keyword`、`date`、地点字段、`temp/wind_speed/wind_deg` 等（`rag/config.py` 的 `KEEP_COLS`）

> 为什么要定义 KEEP_COLS：  
> - RAG 不只需要“检索命中”，还要把命中结果“作为证据呈现”，因此需要保留能解释的元数据；  
> - 同时要控制元数据规模，避免把大量无关字段塞进索引与 UI，影响性能与隐私合规。

### 3.2 清洗策略与理由（`rag/index_builder.py::clean_text_series`）
对文本做最小必要清洗：
- 连续空白归一化为单空格：减少嵌入模型对噪声敏感；  
- `"nan"` 置空：避免把缺失值当作语义内容；  
- 过滤空文本：防止索引中出现“空向量”导致检索异常。

这种“轻清洗”而非“重清洗”的理由是：  
工程事故叙述中的拼写、语法、口语化表达本身携带信息；过度清洗（删掉标点、强行词干化）可能损失危险源、部位、动作等关键信息，从而降低检索召回。

### 3.3 `case_id` 的生成与可追溯性
索引阶段将 `case_id` 设为行号（`df.index.astype(int)`），并在元数据中保存。  
其学术意义在于：**RAG 输出的 citations 不是“参考文献式的模糊引用”，而是可追溯到具体数据记录的确定性指针**，使得：
- 审计时可复查模型依据；  
- 评估时可统计“引用-结论一致性”；  
- 后续可把 `case_id` 替换为真实工程的工单/隐患编号，兼容企业系统。

## 4. 知识层（RAG）：让大模型“有依据地说”

### 4.1 为什么选择 RAG（而不是只靠大模型生成）
在工程安全/运维管理中，纯生成存在两类高风险：
- **事实幻觉**：模型可能编造不存在的规范或案例；  
- **不可追溯**：无法回答“你为什么这么判断”。  

RAG 的关键价值是把推理约束为：  
**结论 =（用户输入 + 检索证据 + 受控提示词）→ 结构化输出**。  
在方法论上，这是将“黑箱生成”转化为“可审计的证据链生成”。

### 4.2 文本表示：检索文本的拼接策略（`rag/index_builder.py::_compose_retrieval_text`）
索引向量并非只来自 `abstract`，而是拼接以下信息（若存在）：  
`event_keyword` + `event_type` + `abstract` + `description`

这样做的原因：
- `event_keyword` 往往是高度浓缩的危险源标签，能显著提升检索的“主题对齐”；  
- `abstract` 提供上下文细节，帮助语义模型捕捉场景与因果链；  
- 拼接属于“信息增广”，在不改变原始数据的前提下，提高单条记录的可检索性。

### 4.3 向量化模型与关键参数（`rag/embedding.py`、`rag/config.py`）
**默认嵌入模型**：`sentence-transformers/all-MiniLM-L6-v2`  
- 向量维度：384（`HASHING_DIM=384` 与该模型维度对齐）  
- 归一化：`normalize_embeddings=True`（或手动 L2 norm）

为什么选它：  
1) **低成本**：计算量较小，CPU 也可用；符合项目书“普惠部署”；  
2) **通用性**：对短文本检索表现稳定；  
3) **工程可控**：384 维向量在 5 万级样本上索引与检索都较轻量。

**批大小**：`BATCH_SIZE=128`  
理由：  
- 过小会导致 GPU/CPU 吞吐下降；过大则可能在低内存机器上 OOM；  
- 对 5 万级样本，128 是较常见的吞吐/内存折中点。建议范围：64–256（视内存与设备而定）。

**离线兜底嵌入**：HashingVectorizer / simple hash  
理由：  
- 真实部署时可能遇到“模型文件无法下载/缺依赖”，离线 hashing 让系统仍可建立索引与检索，保证可用性；  
- `HASHING_DIM` 与主模型维度一致，避免“维度不一致导致索引不可用”的工程故障。

### 4.4 向量索引：FAISS IndexFlatIP 的选择
索引实现（`rag/index_builder.py`）：
- 索引类型：`faiss.IndexFlatIP(dim)`  
- 相似度：Inner Product（在向量已归一化时等价于 Cosine Similarity）

为什么不用更复杂的 IVF/HNSW：  
- 5 万级样本属于中小规模，`IndexFlatIP` 做**精确检索**成本可接受；  
- 免训练、实现简单、可复现性更强；  
- 复杂近似索引虽更快，但会引入近似误差与调参成本，不利于作为研究原型的“基线系统”。

### 4.5 检索策略：跨语言提示 + 混合重排（`rag/retrieval.py`）
系统面对一个现实问题：事故文本主要为英文，但用户输入多为中文。  
解决办法之一是“轻量跨语言提示”（而不是全量翻译）：
- `ZH_TO_EN_HINTS`：当查询包含“高处/坠落/触电/脚手架/吊装…”等中文关键词时，追加可能的英文关键词提示；
- 这样能让嵌入模型在跨语言时获得更高对齐概率，且不会引入翻译 API 成本。

**混合打分**：  
- 语义得分 `semantic_score`：来自 FAISS inner product；  
- 关键词重叠 `keyword_score`：对 query 与案例文本做 token 化，计算重叠并按 query 长度归一；  
- 混合分 `hybrid_score = 0.85 * semantic + 0.15 * keyword`。

参数解释：  
- `0.85/0.15` 是“以语义为主、关键词为辅”的权重设置：  
  - 语义模型解决同义表达、上下文相似；  
  - 关键词重叠解决专业名词/设备型号/关键动作等“必须命中”的硬约束；  
  - 权重不宜过高（例如 >0.3），否则检索会退化为词面匹配，跨语言与同义表达的优势被抵消。  
  - 建议范围：`keyword_weight` 0.05–0.25，可用离线评测（MRR/Recall@k）校准。

**候选扩展 `search_k`**：  
实现为 `search_k = min(max(top_k, top_k*8), N)`。  
理由：  
- 先用较大候选集保证召回，再用混合分重排；  
- `*8` 是经验折中：候选太少重排无意义；候选太多会浪费延迟。

**输出条数 `top_k=3`（在 `app.py`）**：  
理由：  
- 每条案例会被放入提示词上下文，`top_k` 增大会显著拉长 prompt，增加费用与延迟，并提高“证据噪声”；  
- 对事前预判，3 条高相似案例往往足够提供“模式参考”；  
- 建议范围：3–8。若改为 5/8，需同步评估：prompt token、响应时延、引用一致性。

## 5. 推理层：结构化输出 + 引用约束，降低幻觉与不可控性

### 5.1 提示词模板：把“输出格式”变成硬约束（`rag/prompting.py`）
系统提示词包含强制规则：
- 只能输出有效 JSON（不允许 Markdown/解释文本）；  
- 所有自然语言字段必须为简体中文；  
- 必须至少引用 1 个检索到的 `case_id`；  
- 证据不足要明确写“证据不足”，但仍需引用案例；  
- 必须结合“工种专项信息”进行判断。

为什么这样写：  
- **可解析性**：JSON 是机器可解析结构，便于 UI 展示与派单；  
- **可追溯性**：强制 citations 把“模型依据”固定在检索结果集合里；  
- **抗幻觉**：要求“不编造事实”和“证据不足”是对模型输出边界的显式声明；  
- **领域约束**：工种专项信息是把工程知识显式注入推理上下文，防止模型泛泛而谈。

### 5.2 大模型调用参数（`app.py`、`llm/client.py`）
关键参数（在线模式）：
- `temperature = 0.0`：降低随机性，提升同输入下输出稳定性（工程场景更需要一致性而非创意）；  
- `max_tokens = 800`：保证输出有足够空间覆盖 hazards/measures/PPE/rationale；过大可能带来冗长与成本；建议范围 600–1200；  
- `timeout = 20s`：保证 UI 不长时间卡死；建议范围 15–60s（视网络与模型负载）。

配置方式：
- `DEEPSEEK_API_KEY / DEEPSEEK_BASE_URL / DEEPSEEK_MODEL` 通过环境变量注入；  
- 原则上不应把密钥硬编码在代码仓库中（安全合规与可移植性要求）。

### 5.3 结构化校验：JSON 解析 + schema 校验（`rag/extraction_schema.py`）
系统对模型输出做三步控制：
1) 去除 code fence（兼容模型偶尔输出 ```）；  
2) JSON 解析；  
3) 字段归一化与校验：  
   - `risk_level` / `severity_level` 强制在 `[1,4]`；  
   - 列表字段强制为 `list[str]`；  
   - `citations` 过滤为 `allowed_case_ids` 的子集；  
   - 在 require_citations=True 时，过滤后为空则判失败。

为什么这是关键：  
工程系统的核心问题不是“能不能生成”，而是“能不能稳定地生成可用结果”。  
schema 校验把大模型输出从“自由文本”约束为“可上线的 API 返回值”，从而可以：
- 写单元测试；  
- 做错误重试/降级；  
- 统计字段缺失与错误率，作为持续改进指标。

## 6. 事前预判：模型推理与规则兜底的双通道

### 6.1 双通道的工程意义
项目书强调“低成本、可落地”，意味着系统不能把可用性完全押注在外部大模型上。  
因此 `app.py` 实现如下策略：
- 若检测到 `DEEPSEEK_API_KEY`：走在线推理（RAG + LLM）；  
- 否则：走离线预判（规则模型 `rag/local_pre_assessment.py`），并提示用户当前为离线模式。

这属于典型的**容错设计（fault tolerance）**：  
- 业务连续性优先；  
- 同时保留在线模式的高质量输出。

### 6.2 离线预判的规则模型：阈值与解释（`rag/local_pre_assessment.py`）
规则模型以“基础风险 + 条件加权”的方式计算风险分，再映射到 1–4：

**(1) 工种基础风险 `base_risk`**  
高处/拆除/起重等更高，综合施工较低。  
理由：不同工种固有危险源不同，先验风险不应由环境参数“决定一切”。

**(2) 高度阈值**  
- `work_height >= 5m` 加风险；`>=15m` 再加风险  
理由：  
- 5m 可视为“明显高处作业”分界（已经不再是地面微小跌落）；  
- 15m 体现更高坠落后果与救援难度；  
建议：阈值应结合当地规范与企业标准校准（如脚手架、吊篮作业管理条款）。

**(3) 夜间作业**  
若 `shift` 含“夜”，增加风险。  
理由：可见性下降、沟通成本上升、疲劳因素更显著。

**(4) 新工人占比阈值**  
- `>=25%` 加风险；`>=50%` 再加  
理由：新工人比例反映团队经验结构，影响违章概率与处置效率；阈值用于把“经验不足”显式纳入评估。

**(5) 温度阈值**  
- `temp_c >= 30/35` 增加热应激风险；`temp_c <= 0` 增加滑跌、材料脆裂等风险  
理由：这些阈值是工程管理中常用的气象风险分段点；  
建议范围：  
- 热：30–38°C 分段；冷：0–5°C 分段，需结合地区气候与作业强度。

**(6) 风速阈值**  
- `wind_speed >= 6 m/s` 提示风载影响；`>=10 m/s` 视为强风高风险  
理由：高处与吊装作业对风载敏感，风速阈值可直接触发停工建议；  
建议：阈值应结合吊装方案、设备说明与现场管理制度。

**(7) 湿度阈值**  
- `humidity >= 85%` 增加湿滑/绝缘下降风险  
理由：高湿与降雨往往同时出现，滑跌与触电风险上升；阈值用于早期提示。

> 规则模型的定位：  
> - 不是追求“预测最准确”，而是提供**可解释、可用、可离线**的基线策略；  
> - 并为在线模型提供“阈值可解释框架”，便于管理者理解。

### 6.3 组合风险分（0–100）与分段（`app.py::risk_score`）
系统把 `risk_level` 与气象影响合成为可视化分数：

1) 严重度归一化：`severity_norm = (level - 1) / 3`  
2) 气象影响：`climate_impact = clip( (temp_score + wind_score)/2 , 0, 1 )`  
   - `temp_score = max(0, temp_c - 25) / 15`（以 25°C 为舒适基线，15°C 为归一化尺度）  
   - `wind_score = wind_speed / 15`（以 15 m/s 为归一化尺度）  
3) 合成：`score = 100 * clip( 0.7*severity_norm + 0.3*climate_impact , 0, 1 )`

关键参数解释：  
- **权重 0.7/0.3**：风险等级（来自作业与管理因素）在安全管理中通常是主导因素；气象是“加剧器/触发器”，因此占比更小。  
  - 若场景更偏“极端气象下运维”（如台风抢修），可提高气象权重到 0.4–0.6。  
- **温度基线 25°C、尺度 15°C**：把常见温度区间压到 0–1，避免温度对分数的过度放大；  
- **风速尺度 15 m/s**：覆盖多数工地风速分布的上界；更极端的风速会被 clip 限制，避免分数爆炸。

分段阈值：
- `<45` 低风险，`45–74.9` 中风险，`>=75` 高风险  
理由：  
- 三段法匹配管理动作的三类策略（常规/加强/停工或专项管控）；  
- 阈值可用历史事故统计做敏感性分析后校准（例如让高风险段覆盖事故后果最严重的前 10–20% 场景）。

## 7. 应用层工程化：交互、可视化、数据管理与运行方式

### 7.1 Streamlit 作为快速原型框架（`app.py`）
选型理由：
- 快速把“模型输出”转化为“可用界面”，便于项目书所需的场景验证与反馈收集；  
- 纯 Python 技术栈，降低开发成本；  
- 易与数据分析图表（Plotly）集成，支持研究型可视化。

### 7.2 数据上传与索引重建（`app.py`）
系统支持上传补充 CSV 并重建索引，关键约束：
- 必须包含 `TEXT_COL=abstract`；  
- 建议包含 `event_keyword` 与 `degree_of_inj_x`（用于检索与统计）。

为什么要做“重建索引”而不是“在线增量写入”：  
- 简化一致性：FAISS Flat 索引虽可 add，但同时还要维护元数据一致性与持久化；  
- 研究原型阶段更重视可复现与确定性，重建更稳健；  
- 后续若需要增量，可引入追加写入 + 周期性重建的混合策略。

### 7.3 传感数据接口（`sensors/api.py`）
当前实现为 mock，并明确预留三种接入方式：
- MQTT：工地常见；  
- HTTP/REST：气象站或第三方天气 API；  
- 串口：本地硬件传感器。

参数范围设置（UI）：
- 温度：-10 到 45°C；风速：0 到 20 m/s；湿度：0 到 100%  
理由：覆盖多数施工环境可能范围，并保持仪表盘显示稳定；极端值可在后续按地区扩展。

## 8. 评估与验证：从“能跑”到“可信”

### 8.1 单元测试（`tests/`）的意义
系统提供多类测试，覆盖“可解析性、契约一致性、离线兜底、因果模块 sanity”：
- `test_extraction_schema.py`：结构化抽取字段与范围校验；  
- `test_rag_contract.py`：citations 必须来自检索结果集合；  
- `test_pre_assessment_prompt.py`：提示词必须包含工种专项信息（防止回归为通用模板）；  
- `test_local_pre_assessment.py`：离线预判输出完整性；  
- `test_psm_sanity.py`：合成数据下估计方向正确（ATE<0）。

为什么在工程管理系统中必须做测试：  
输出的错误不是“页面崩溃”那么简单，可能导致错误处置建议或错误停工决策；测试是把风险控制前移到研发阶段的必要手段。

### 8.2 验收脚本（`scripts/verify_pipeline.ps1`）
提供端到端“冒烟测试”：
1) 检查环境变量；  
2) 小样本结构化抽取；  
3) 运行 PSM；  
4) 检查产物文件生成。  

这体现了研究型系统的规范：**每一次交付都应能在新环境中被复跑验证**。

### 8.3 PSM 因果分析模块：参数与解释（`analysis/causal_psm.py`）
模块目的：对“投诉驱动检查（treatment）是否降低未来事故（outcome）”做因果效应估计示范。  
核心方法：  
- Logistic 回归估倾向得分（含 `StandardScaler`）；  
- 1-NN 最近邻匹配；  
- `caliper` 限制匹配差距；  
- bootstrap 置信区间。

关键参数：
- `caliper=0.08`（默认）：  
  - caliper 越小，匹配更严格、偏差更小，但样本会减少；  
  - caliper 越大，样本更多但可比性变差；  
  - 0.05–0.2 是常见探索区间，应以“匹配对数/平衡性指标”共同决定。  
- `bootstrap_iters=200`：  
  - 次数越多 CI 越稳定但耗时更高；  
  - 30–300 为常用范围；研究报告可用 200，快速验收可用 30–80。  
- `seed=42`：固定随机性保证复现。

> 为什么把因果模块放进系统：  
> 工程管理研究往往需要回答“某管理措施是否有效”，而不仅是“能否预测”。  
> 将 PSM 工具链内置，能把系统从“智能助手”推进到“可评估的管理干预研究平台”。

## 9. 部署与交付：低门槛运行与桌面化打包

### 9.1 运行模式 1：开发/研究环境一键启动（`scripts/start_app.py`）
特点：
- 依赖安装在项目目录 `.runtime_packages`，避免污染全局 Python；  
- 自动构建索引（若不存在）；  
- 启动 Streamlit 服务并打开浏览器。

这种模式的意义：  
在高校创新训练项目中，团队成员设备与环境差异大；“本地隔离依赖 + 自动索引”能显著降低协作成本。

### 9.2 运行模式 2：桌面化交付（`launcher.py` + PyInstaller）
打包关键点：
- 用 `CSDATASET_HOME` 指向可写的数据目录（如 `%LOCALAPPDATA%/.../Data`）；  
- 首次运行将种子数据（CSV、indexes）复制到用户目录；  
- 写入本地 Streamlit 配置，关闭统计并 headless；  
- 保留 `launcher.log` 用于故障定位。

为什么要这样设计：  
- 研究原型要“可交付给非技术用户试用”；  
- 工程系统需要可写目录存储索引、上传数据、运行日志；  
- Windows 环境下 `%LOCALAPPDATA%` 是更规范的应用数据位置。

## 11. 局限性与后续扩展（与项目书技术路线对齐）

### 11.1 当前系统局限（必须在论文中如实陈述）
- 多模态范围主要覆盖“文本 + 环境参数”，图像/视频/振动等尚未纳入主链路；  
- 资源调度网络与 DRL/数字孪生尚未实现；当前仅提供分级建议与可扩展派单接口；  
- 在线持续学习、联邦学习、知识图谱在本仓库中仅作为技术路线目标，未形成闭环。

### 11.2 迭代路线（建议按“可复现增量”推进）
1) **多模态接入**：在 `sensors/` 下扩展真实 MQTT/HTTP；新增 CV 模块处理摄像头画面（安全帽/临边防护等）；  
2) **知识图谱**：将 `case_id` 与危险源/措施形成三元组，支持规则与 RAG 的联合检索；  
3) **资源调度与干预评估**：把派单执行记录、整改闭环数据纳入表结构，PSM/DiD 用真实数据评估干预；  
4) **在线学习**：引入反馈采集（采纳/不采纳、事故发生与否）作为持续校准数据；  
5) **隐私与共享**：若跨项目协同，采用联邦学习/隐私计算框架，满足项目书“共享但不泄露”的目标。
