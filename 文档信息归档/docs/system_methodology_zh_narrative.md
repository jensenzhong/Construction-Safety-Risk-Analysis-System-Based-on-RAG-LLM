# 基于 AI 智能分析的工程项目精细化运维（安全）管理系统：开发与实现方法论（叙述版）

本系统的开发以《广州大学大学生创新训练项目申报书.docx》中“人工智能技术与工程项目运维管理深度融合”的总体目标为牵引，围绕传统工程管理中“数据割裂难分析、外部风险响应慢、动态管控不精准”的典型痛点，将研究问题重构为可计算、可验证、可部署的工程化任务链条。需要强调的是，项目书提出的愿景覆盖多模态风险识别、韧性资源调度网络、知识共享与预测性维护等多模块协同的全链路体系；而本仓库的实现选择了其中最具可落地性、同时最能体现“数据智能驱动”的核心切片作为原型：以历史事故知识库为证据基础，结合环境参数与作业计划信息，在作业开始前输出结构化的风险评估报告，并通过检索增强生成（RAG）机制提供可追溯的引用依据，以满足工程安全管理中“可解释、可审计、可执行”的要求。在方法论上，这种“从全景目标中切分出最小可验证系统（MVP）”的策略并非降低研究雄心，而是为了确保阶段性成果能够被复现、被评估、被推广，并为后续多模态扩展与调度优化模块提供稳定的接口与数据基础。

系统设计的第一步是需求工程的形式化：将工程管理问题翻译为机器可处理的输入—输出契约。工程运维与安全管理的难点往往不在“是否能生成一段建议”，而在于建议能否被流程化执行、能否与派单与复盘对接、能否在审计时回答“依据是什么”。因此，本系统将“事前预判”场景定义为输入端包含作业计划文本（work_plan）、工种类型（trade_type）、工种专项信息（例如高处作业的临边防护状态、安全带挂点类型；电气作业的 LOTO 执行状态、绝缘检测状态等）、以及实时或手动采集的环境参数（温度 temp_c、风速 wind_speed、湿度 humidity）。输出端则被约束为结构化 JSON：风险等级 risk_level（1–4）、主要潜在危险源 potential_hazards、针对性预防措施 preventive_measures、必需 PPE required_ppe、引用案例 citations（必须来自检索结果的 case_id 集合）、以及用于解释等级与措施选择依据的 rationale。风险等级采用 1–4 的离散标尺，原因在于其同时兼顾管理动作分级的可操作性、标注与统计的稳定性，并与现有事故数据集中常见的严重度字段（如 `degree_of_inj_x`）自然对齐，使得后续的可视化分析与阈值校准具有数据依据。更重要的是，结构化输出为测试与验收提供了客观标准：系统不是“看起来像对的”，而是“字段齐全、范围合法、引用可追溯、可以直接进入管理流程”。

在数据层与知识层的实现上，本系统采取“最小必要清洗 + 可追溯标识”的策略来对抗工程数据的“脏乱差”。历史事故数据以 `Injury Severity.CSV` 为核心数据源，其中事故叙述文本主要集中在 `abstract` 列（配置为系统的 TEXT_COL），并辅以 `event_keyword`、时间地点与部分环境字段作为元数据。索引构建阶段并不追求过度的文本规范化，而是进行轻量清洗：将连续空白归一、将字符串形式的缺失值置空并过滤空文本条目，避免“噪声驱动嵌入”与“空文本进入索引”导致检索不稳定。与此同时，系统将每条记录赋予确定性的 `case_id`（以行号生成并固化到元数据中），使得后续所有推理结论都可以通过 citations 回指到具体案例记录。这一点在工程管理研究中具有关键意义：它把大模型输出从不可追溯的“经验性建议”转换为可审计的“证据链驱动决策”，从而使系统能够进入真实组织流程并接受责任边界的检验。

RAG 的核心在于“先检索、后生成”，其目的并非简单提高回答相关性，而是以检索到的历史案例作为推理边界与事实约束，显著降低纯生成模型在专业领域的幻觉风险。索引构建采用 sentence-transformers 的轻量嵌入模型（默认 all-MiniLM-L6-v2），主要考虑到工程现场常见部署环境（CPU 为主、成本敏感）以及 5 万级样本规模下的计算可行性。该模型输出向量维度为 384，因此系统的 fallback 表征也统一到 384 维（HASHING_DIM=384），在嵌入模型不可用或离线场景下启用 HashingVectorizer 或 simple hash 作为兜底，保证索引维度一致，从工程角度避免“索引已建但运行时嵌入维度不匹配”这种典型的线上故障。嵌入阶段设置批大小 BATCH_SIZE=128，是在吞吐与内存之间的折中：对 5 万条样本而言，批次过小会显著降低编码效率，批次过大则容易在低内存设备上产生不稳定；经验上 64–256 是可调区间，实际部署可按硬件资源与运行时峰值内存校准。向量索引选用 FAISS 的 IndexFlatIP（内积）作为基线结构，其优势是精确检索、无需训练、行为确定性强；当向量经过 L2 归一化时，内积与余弦相似度等价，这使得“相似度”在解释上更直观，同时避免了近似索引（IVF/HNSW）带来的额外调参与可重复性成本。鉴于样本规模并不巨大，Flat 结构的延迟在研究原型与轻量系统中可接受，并且更适合作为后续引入近似检索的对照基线。

检索阶段的关键挑战来自语言与表达差异：数据集中事故叙述主要为英文，而系统使用者在本地场景中往往输入中文作业计划与风险描述。为了在不引入外部翻译成本的前提下提高跨语言检索的对齐度，系统采用“关键词触发的轻量跨语言提示”策略：当查询文本包含“高处、坠落、触电、脚手架、吊装、坍塌”等高频工程风险关键词时，追加可能对应的英文关键词提示，作为嵌入输入的一部分，提升语义编码阶段捕捉到正确语义域的概率。检索结果并不完全依赖向量相似度，而是引入“语义得分 + 关键词重叠”的混合重排：语义得分来自 FAISS 内积，关键词得分通过对 query 与案例文本进行 token 化后计算重叠比例，并以 query 长度归一化以避免长文本偏置。混合权重设定为 0.85（语义）与 0.15（关键词），其背后的假设是语义检索承担“同义表达与上下文相似”的主要任务，而关键词重叠用于强化专业名词与关键动作的硬约束；如果关键词权重过高，检索会退化为词面匹配并削弱跨语言与语义泛化能力，因此建议在 0.05–0.25 区间结合离线指标（Recall@k、MRR）进行校准。为了让重排有效，系统先从索引中取出更大的候选集（例如 top_k 的 8 倍）再重排，这是典型的“召回—排序”两阶段架构：候选太少重排无意义，候选太多则增加延迟；在 5 万级数据下，该策略为准确率与时延提供了可解释的折中。

在推理层，本系统将“大模型能力”严格封装为“结构化抽取器”，而不是让其输出无法校验的长篇自然语言。提示词模板对输出形式与内容约束进行了硬化：要求只能输出有效 JSON、自然语言字段使用简体中文、必须至少引用一个来自检索结果的案例 ID、不得编造事实并在证据不足时明确声明，同时要求结合“工种专项信息”进行判断。这样的提示词约束并不是形式主义，而是对工程安全场景中“结论必须可用、必须可追责”的工程化响应：一旦输出可解析为 JSON，就可以被 UI 稳定展示、被派单逻辑消费、被日志记录用于追溯；一旦强制 citations 且限定在检索结果集合内，就将模型的证据空间限制在可复查的数据子集，从机制上压缩了幻觉的自由度。为了进一步降低不确定性，在线推理调用参数采用 temperature=0.0，使同输入下的输出尽可能稳定一致；max_tokens 设置为约 800，以覆盖风险等级、危险源、措施、PPE 与理由等字段的必要长度，同时避免输出冗长导致成本与延迟失控，实践中 600–1200 可作为可调范围；timeout 约 20 秒则是 UI 交互与网络不确定性之间的折中，过长会导致用户等待不可接受，过短会增加失败率。需要指出的是，大模型并不直接决定系统是否可用，因此系统引入了离线预判通道作为兜底：当环境中缺少 API Key 或在线调用失败时，系统自动切换到规则模型生成风险报告，并在界面提示当前为离线模式。这种“双通道推理”体现了工程系统的可靠性设计思想：把在线模型作为性能与质量的增益，而不是把业务连续性完全依赖外部服务。

离线预判模型采用“工种基础风险 + 条件加权”的可解释规则体系，并通过阈值与分段将经验知识显式化。不同工种具有不同固有风险，规则模型为高处作业、起重吊装、拆除等设定更高 base_risk，是对“危险源先验”与管理经验的形式化表达；随后根据作业高度、班次、新工人占比与环境参数对风险分做增量修正：例如将 5m 作为高处作业的显著分界，将 15m 作为后果更严重与救援更复杂的分界；将夜间作业视为可见性降低与疲劳风险上升的指标；将新工人占比在 25% 与 50% 两个节点加权，是对团队经验结构影响违章概率与处置效率的反映；将温度在 30/35°C 与 0°C 附近分段，对应热应激与低温滑跌、材料性能变化等风险；将风速在 6m/s 与 10m/s 附近分段，则是高处与吊装作业对风载高度敏感的工程事实表达，并可直接触发“暂停高处作业与起重吊装”等管理动作建议。规则模型不以“预测精度最优”为目标，而以“在离线条件下仍能提供可执行且可解释的基线策略”为目标；同时，它为在线模型提供了一个可解释的参照框架，使管理者能够理解模型输出背后的风险逻辑而非将其视为不可控黑箱。

为了在界面中形成直观的风险量化指标，系统将风险等级与气象影响合成为 0–100 的综合风险分，并按阈值映射到“低/中/高”三段。具体而言，风险等级被归一化为 severity_norm=(level−1)/3，气象影响通过温度与风速的归一化函数得到 climate_impact，其中温度以 25°C 为相对舒适基线并以 15°C 为尺度进行归一化，风速以 15m/s 为尺度归一化，二者取平均并裁剪到 [0,1]；综合风险分采用 0.7×severity_norm + 0.3×climate_impact 的加权组合并映射到 0–100。将严重度权重设为 0.7 的理由在于作业类型、管理状态与人员因素通常构成事故风险的主导项，而气象更常作为“加剧器/触发器”，因此在一般施工场景中占比应更低；若研究对象转向极端气象运维（如台风抢修），则可以通过实证数据提高气象权重至 0.4–0.6 并重新校准阈值。风险分段阈值设置为 <45 低风险、45–74.9 中风险、≥75 高风险，其管理含义是为不同段提供不同强度的控制策略（常规、加强、暂停或专项管控），同时为后续用历史数据进行灵敏度分析与阈值优化预留了空间。通过将模型输出进一步量化与分段，系统实现了从“建议文本”到“管理指标”的过渡，使其能够更自然地进入工程项目的 KPI 与过程控制体系。

在应用层实现上，系统采用 Streamlit 构建交互界面，以较低的工程成本完成数据可视化、参数输入、模型推理触发与结果报告展示。选择 Streamlit 的原因在于其能以纯 Python 快速迭代研究原型，便于项目书要求的场景验证与反馈收集，同时易于与 Plotly 等可视化组件集成，用于展示事故统计分布、环境与严重度关系、以及相似案例内容等信息。系统同时提供数据管理能力：允许用户上传补充 CSV 并在必要时重建索引，上传时强制包含 `abstract` 列并建议包含 `event_keyword` 与严重度字段，以保证检索与统计的可用性。索引重建而非增量写入的选择，体现了研究原型阶段对一致性与确定性的偏好：重建虽然在大规模数据下代价更高，但在当前规模下可以换取更少的状态复杂度与更低的错误概率，并减少“索引与元数据不一致”带来的隐性风险。环境传感数据接口目前以 mock 实现，但在模块设计上明确预留 MQTT、HTTP/REST、串口等接入方式，符合项目书“硬件软件结合、边缘与现场数据采集”的路线，并为未来真实工地或校园场景试点提供可扩展路径。

为了保证系统的学术规范与工程可复现性，本仓库将评估与验证作为方法论不可分割的一部分，而不是开发完成后的附加环节。首先，针对结构化输出契约与 RAG 引用约束编写了单元测试：一方面检验 JSON schema 的字段齐全性与取值范围（例如风险等级必须在 1–4），另一方面检验 citations 必须来自检索到的 case_id 集合，从而在机制层面保证“可追溯证据链”不会因提示词漂移或解析器回归而失效；同时也对离线预判输出的完整性进行测试，确保在无在线服务条件下系统仍能返回符合契约的报告。其次，系统提供端到端验收脚本，用小样本抽取与因果分析的结果文件生成来做冒烟测试，这使得系统可在不同机器、不同成员环境中稳定复跑。更进一步，为了呼应项目书中“管理措施有效性评估”的研究需求，系统内置了轻量 PSM（倾向得分匹配）因果分析模块，以合成数据先行实现并预留真实数据接入口：通过逻辑回归估计倾向得分、采用 1-NN 最近邻匹配并以 caliper 限制匹配差距，再通过 bootstrap 给出 ATT/ATC/ATE 的置信区间。caliper 默认取 0.08，体现偏差与方差之间的折中：阈值过小会导致匹配对不足、估计不稳定，阈值过大则会引入不可比样本提高偏差；bootstrap 迭代次数默认 200，是在置信区间稳定性与计算成本之间的平衡，快速验收可降至 30–80，而正式报告可维持 200 或更高并配合平衡性诊断。将因果分析纳入系统方法链条的意义在于，它把研究从“能预测/能建议”推进到“能评估干预效果”，为后续在真实工程数据上验证管理策略提供可复用工具。

在交付与部署方面，系统同时考虑研究环境与非技术用户试用的双重需求。研究环境下，启动脚本将依赖安装到项目目录中的运行时包路径，避免污染全局 Python，并在缺失索引时自动构建索引，降低成员协作的环境摩擦；面向试用与展示，则通过 PyInstaller 将应用打包为桌面启动器，并将数据与索引复制到用户可写目录，配合本地日志记录与浏览器自动打开，实现“安装—点击—运行”的低门槛体验。这样的部署策略与项目书强调的“低成本、开源、可推广”目标一致：系统不要求复杂的服务器与运维环境即可运行，同时为后续接入真实传感器、扩展多模态识别与调度优化留下工程空间。

最后，从学术规范的角度，本系统必须在论文或结题报告中明确陈述当前实现与项目书愿景的边界：当前原型的多模态主要体现在“文本 + 环境参数”的融合，尚未把图像/视频/振动等多源信号纳入统一表征与融合模型；资源调度网络与深度强化学习、数字孪生等模块尚处于方法规划与接口预留阶段，未形成可运行闭环；在线持续学习、联邦学习与知识图谱等能力也需要以真实场景数据与组织协作机制为前提才能落地。基于本仓库建立的结构化输出契约、RAG 证据链机制与可复现的评估框架，后续工作可按“先可用、再增强、再优化”的顺序推进：先在 `sensors/` 接入真实数据源并建立数据质量控制流程，再引入视觉识别模块与知识图谱以提高危险源覆盖与可解释性，随后将派单与整改闭环数据纳入数据库并用因果方法评估干预策略效果，最终在合规与隐私约束下探索跨项目知识共享与在线学习机制。通过这种循证、可复现的迭代路线，系统能够在不牺牲学术严谨性的前提下逐步逼近项目书提出的全链条智能化工程运维目标。
